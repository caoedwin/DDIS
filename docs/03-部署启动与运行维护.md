## 3.2 启动命令

### 3.2.1 开发服务器（HTTP）

```bash
python manage.py runserver 0.0.0.0:8000
```

> **注意**：开发服务器使用 `runserver` 时**不支持 WebSocket**（需 ASGI + Daphne）。
> 生产环境请使用 Daphne（见 3.2.2）。

### 3.2.2 WebSocket / Channels（ASGI）

```bash
# 推荐方式：使用项目提供的批处理
ChannelsServer.bat
# 或手动执行：
C:\Python372\mecheck\Scripts\daphne.exe -b 0.0.0.0 -p 8000 Reliability_Row_data.asgi:application
```

> [ChannelsServer.bat](../ChannelsServer.bat) 中绑定为 `127.0.0.1:8700`，生产部署前需修改 `-b` 与 `-p`。
> 当使用 Daphne 时，HTTP 与 WebSocket 共用同一端口，无需另开 runserver。

### 3.2.3 Celery Worker

```bash
# 使用批处理
DDISceleryworker.bat
# 或手动执行
C:\Python372\mecheck\Scripts\celery.exe worker -A Reliability_Row_data -l info -P eventlet
```

> [DDISceleryworker.bat](../DDISceleryworker.bat) 中工作目录为 `C:\djangoproject\Reliability_Row_data`，使用 eventlet 池。
> 必须先启动 Redis 才能启动 Worker。

### 3.2.4 Celery Beat（定时任务调度）

```bash
# 使用批处理
DDIScelerybeat.bat
# 或手动执行
C:\Python372\mecheck\Scripts\celery.exe -A Reliability_Row_data beat -l info
```

> [DDIScelerybeat.bat](../DDIScelerybeat.bat) 会先删除 `celerybeat.pid`，避免 PID 冲突。
> Beat 必须与 Worker 在同一项目目录下启动。

### 3.2.5 生产部署（IIS + wfastcgi）

- 部署平台：Windows + IIS
- WSGI 网关：wfastcgi 3.0.0
- web.config 示例见 [settings.py](../Reliability_Row_data/settings.py) 中注释（最大请求 1GB、超时 1 小时）。
- 生产环境应将 `DEBUG = False`，但当前 `DEBUG = True`，迁移到生产前必须修改。

## 3.4 维护检查清单

### 3.4.1 日常检查（每日）

| 项 | 检查方式 | 期望结果 |
|----|----------|----------|
| Web 服务存活 | `curl http://localhost:8000/login/` | 返回登录页 HTML |
| Celery Worker 心跳 | 检查 `scheduleflag.txt` 修改时间 | 与当前时间差 < 2 分钟 |
| Celery Beat 运行 | 检查 `celerybeat.pid` 存在 | 文件存在 |
| Redis 连接 | `redis-cli -a DCT2019 ping` | `PONG` |
| MySQL 连接 | `mysql -u edwin -pDCT@2019 -e "SELECT 1"` | 返回 1 |
| 当日日志生成 | 查看 `logs/all-YYYY-MM-DD.log` | 文件存在且有内容 |
| 磁盘空间 | 检查 `c:\` 与 `c:\media` | 至少 10GB 可用 |
| 上传目录可写 | 测试上传到 `c:\media` | 成功 |

### 3.4.2 周检查（每周）

| 项 | 检查方式 |
|----|----------|
| 项目同步任务执行 | 查看 `logs/ProjectSync-YYYYMMDD.txt` 是否每周一至五生成 |
| 邮件提醒任务执行 | 检查 `logs/all-*.log` 中 `Mailhtml` / `MailOAtest` 输出 |
| Exchange 账号配置 | 确认 `OAmail_account.json` 仍可登录（手动触发一次 CriticalIssue 邮件） |
| 日志清理 | `logs/` 目录文件数量过多时归档备份 |
| 数据库备份 | `mysqldump -u edwin -p reliabilityrowdata > backup-YYYYMMDD.sql` |
| Admin 后台异常登录 | 查看 `django.request` logger / `logs/error-*.log` |

### 3.4.3 月度检查

| 项 | 检查方式 |
|----|----------|
| Session 表清理 | Django `python manage.py clearsessions` |
| DB 数据完整性 | `python manage.py inspectdb` 与模型对比 |
| 依赖安全 | 检查 `requirements.txt` 中关键包是否有已知 CVE（不自动升级） |
| Redis 内存使用 | `redis-cli -a DCT2019 INFO memory` |
| MongoDB 数据 | 业务很少使用，可略过 |

### 3.4.4 紧急检查清单（系统不可用）

按顺序排查：

1. **网络/服务端口** —— Redis 6379 / MySQL 3306 / 应用 8000 是否监听
2. **Python 虚拟环境** —— `c:\Python372\mecheck\Scripts\` 下 celery/daphne 可执行
3. **settings.py 是否被改动** —— 与 `base20250911backup.html` 类似，确认 settings 未被破坏性修改
4. **`scheduleflag.txt` 时间戳** —— 若过旧，Celery Worker 已停
5. **`logs/error-*.log` 最新错误** —— 定位异常堆栈
6. **`logs/all-*.log` 最后输出** —— 看是否在某个请求处卡死
7. **`celerybeat.pid` 是否残留** —— 删除后重启 Beat

## 3.5 常见故障排查

### 3.5.1 登录失败 / 重定向循环

**症状**：访问任何页面都被重定向到 `/login/`，登录后仍跳回登录页。

**排查**：
1. 检查 `UserInfo` 表中账号是否存在：`SELECT * FROM app01_userinfo WHERE account='edwin';`
2. 检查 session 表：`SELECT * FROM django_session WHERE session_key LIKE '%is_login%';`
3. 检查 `settings.SESSION_ENGINE` 是否为 `db`，且 `django_session` 表存在。
4. 检查浏览器 Cookie 是否被禁用。
5. 检查 `SAFE_URL` 中是否包含当前访问的 URL，若包含但用户未登录也会被放行。

### 3.5.2 无权限访问（NoPerm.html）

**症状**：访问业务页面跳转到无权限页。

**排查**：
1. 在 DEBUG 模式下页面会列出可访问 URL，对照用户角色配置。
2. Admin 后台检查 `UserInfo.role → Role.perms → Permission.url` 是否包含目标 URL。
3. 注意 `Permission.url` 是**正则字符串**，`re.match` 是从开头匹配；`/CDM/CDM_search/` 与 `/CDM/CDM-search/`（连字符不同）会不匹配。
4. 重新登录刷新 session（`SESSION_SAVE_EVERY_REQUEST=True`，但权限变更需重新登录才会重新 init_permission）。

### 3.5.3 Celery 任务不执行

**症状**：定时同步未执行、邮件未发出、`scheduleflag.txt` 不更新。

**排查**：
1. 检查 Celery Worker 进程：`tasklist | findstr celery`。
2. 检查 Beat 进程：`tasklist | findstr celery`，应有 2 个 celery 进程。
3. 检查 Redis DB1 是否有任务：`redis-cli -a DCT2019 -n 1 KEYS "*"`。
4. 检查 `celerybeat.pid` 是否存在但 Beat 未运行（残留 PID），删除后重启。
5. 检查 `celerybeat-schedule.dat` 是否损坏，删除后重启 Beat。
6. 查看 Worker 终端输出是否有 `ConnectionError` 或 `ModuleNotFoundError`。
7. 检查 `app01/tasks.py` 中导入的模块是否全部可导入（如 `CriticalIssueCrossCheck.models` 是否存在）。

### 3.5.4 WebSocket 连接失败

**症状**：前端 `ws://host:8000/ws/msg/xxx/` 连接失败。

**排查**：
1. 必须使用 Daphne（ASGI）启动，不能用 `runserver`。
2. 检查 `Reliability_Row_data/routing.py` 与 `app01/routing.py` 是否完好。
3. 检查 Redis DB14 连接：`redis-cli -a DCT2019 -n 14 PING`。
4. 检查 `asgi.py` 中 `application = ProtocolTypeRouter(...)` 与 `routing.py` 一致。
5. 浏览器控制台查看具体错误码；404 说明路由不匹配，500 说明 consumer 异常。

### 3.5.5 文件上传失败 / 500 错误

**症状**：Excel / 图片上传返回 500。

**排查**：
1. 检查 `c:\media` 目录是否存在且可写（`MEDIA_ROOT = r'c:/media'`）。
2. 检查 `FILE_UPLOAD_MAX_MEMORY_SIZE = 524288000 * 2`（1GB）是否被 IIS 限制覆盖。
3. 查看是否是 CSRF Token 缺失（POST 请求需要 `@csrf_exempt` 或正确携带 token）。
4. 检查 `middleware/UserIP.py` 中 `process_response` 是否因 `json.loads` 报错（已注释掉该段，但仍可能因 logger.critical 失败）。
5. 检查 `DATA_UPLOAD_MAX_NUMBER_FIELDS = 5000`，字段过多会被拦截。

### 3.5.6 邮件发送失败

**症状**：`Mailhtml` / `MailOAtest` 任务执行但邮件未收到。

**排查**：
1. QQ SMTP：检查 `EMAIL_HOST_PASSWORD`（授权码）是否过期。
2. Exchange：检查 `OAmail_account.json` 中账号密码是否正确。
3. 检查 `Tasklogs/Pass-*.log` 与 `Tasklogs/Error-*.log`（由 `Mailsend` 写入）。
4. 检查 Exchange 服务器网络可达：`telnet webmail.compal.com 443`。
5. 内网 SMTP：检查 `10.128.2.181:25` 可达，且发件人 `DDIS_Admin@Compal.com` 已被 IT 授权。

### 3.5.7 前端样式错乱 / 子页面样式失效

**症状**：修改 `base.html` 后子页面 `.wrap-text:hover` / `.my-table` 背景失效或页面不可用。

**排查**：
1. **立即回滚** `base.html` 到 `base20250911backup.html`（已知可正常工作版本）。
2. 检查浏览器控制台是否有 `Uncaught SyntaxError: Unexpected token '<'`（通常是模板里混入了被 Django 渲染的 `<` 字符）。
3. 检查 `static/` 资源 404（如 `jquery.dataTables.js`），确认路径正确。
4. 修改 `base.html` 时**必须使用 scoped class**，不可全局覆盖子页面样式。

### 3.5.8 Django / Python 兼容性错误

**症状**：`ImportError` / `AttributeError` / 模板渲染异常。

**排查**：
1. Django 2.1.7 与 Python 3.12 存在已知兼容性风险，核心代码修改需充分测试。
2. 不要使用 Django 2.2+ 才有的 API（如 `jsonfield` 必须用 `django_jsonfield`）。
3. `from django.conf.urls import url` 仍可用（Django 2.1），但新代码建议用 `re_path`。
4. 检查 `__init__.py` 中 `pymysql.install_as_MySQLdb()` 是否被误删。

## 3.7 备份与恢复

### 3.7.1 必须备份的内容

| 内容 | 路径 / 来源 | 备份方式 |
|------|-------------|----------|
| 源代码 | 项目根目录 | Git 仓库或压缩归档 |
| MySQL 数据库 | `reliabilityrowdata` 库 | `mysqldump -u edwin -p reliabilityrowdata > reliabilityrowdata-YYYYMMDD.sql` |
| 用户上传文件 | `c:\media` | 压缩或同步到备份盘 |
| Exchange 邮件配置 | `OAmail_account.json` | 复制到安全位置 |
| Celery 调度状态 | `celerybeat-schedule.dat` | 可选，损坏可重建 |
| 历史模板备份 | `templates/base*.html` | 不要删除，是回滚依据 |

### 3.7.2 恢复流程

1. 恢复源代码（解压或 `git checkout`）。
2. 恢复 MySQL：`mysql -u edwin -p reliabilityrowdata < reliabilityrowdata-YYYYMMDD.sql`。
3. 恢复上传文件到 `c:\media`。
4. 恢复 `OAmail_account.json`。
5. 启动 Redis / MySQL / MongoDB。
6. 启动 Daphne / Celery Worker / Celery Beat。
7. 验证：访问 `/login/`、Admin、`scheduleflag.txt` 心跳。

## 3.8 升级与变更约束

> **核心约束**：不可随意升级以下版本，升级前必须做完整回归测试。

| 组件 | 当前版本 | 升级风险 |
|------|----------|----------|
| Django | 2.1.7 | 高，与 Python 3.12 已有兼容性风险；升级到 2.2+ 需修改 `url()` → `re_path()` 等 |
| Python | 3.12.9 | 中，与 Django 2.1.7 不在官方支持矩阵 |
| Vue.js | 2.6.10 | 极高，升级到 Vue 3 需重写所有前端 |
| Element UI | 2.12.0 | 极高，升级到 Element Plus 需 Vue 3 |
| DRF | 3.11.0 | 中，新版 API 变更较多 |
| Celery | 4.4.2 | 中，Celery 5.x 配置项命名变化 |
| Channels | 2.2.0 | 中，Channels 3.x 路由写法变更 |
| MySQL | — | 数据库版本变更需检查字符集与排序 |
| Redis | 5.0.1 | 低，向前兼容 |

**变更流程**：
1. 在测试环境完整部署并运行回归测试。
2. 备份生产数据库与代码。
3. 选择维护窗口部署。
4. 部署后立即执行 [3.4.4 紧急检查清单](#348-紧急检查清单系统不可用)。
5. 保留回滚能力至少 24 小时。
